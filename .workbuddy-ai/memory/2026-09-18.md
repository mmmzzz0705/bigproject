### 根因深挖（已定性）：Milvus drop 是异步 GC，容器关闭打断 → 同名僵尸集合累积

`etcdctl get --prefix --keys-only by-dev/meta/root-coord/database/collection-info/1/`
下**有 4 个同名 `gov_docs`**，元数据（fields / `datacoord-meta/s` / `binlog`）**全都还在**：

| collectionID | segments | binlogs | 由来 |
|---|---|---|---|
| 469090338713070002 | 9 | 90 | 僵尸① 768 维旧库（09-15 02:32） |
| 469097101481960460 | 29 | 290 | 僵尸② 853 条曾在此（09-15 09:38~09-17） |
| 469160056362369150 | 2 | 20 | 僵尸③ 今早后端启动建的 |
| **469162635632669586** | **46** | **460** | **当前有效**（今天重灌建的） |

注意：重灌 `--clear` 也会 drop+create，所以每次重灌都会**再留一个僵尸**。

**机制**：`drop_collection()` 只在 rootcoord 打删除标记，etcd 的 collection-info /
fields / segment / binlog 与 MinIO 对象都由**后台 GC 异步清理**。容器一关 GC 就断，
元数据永久残留。残留集合与新建集合**同名**，于是：
- **rootcoord**（权威）按名字 `gov_docs` 只认当前那个 → 旧 ID 查就是 `collection not found`
- **datacoord/querycoord** 从 etcd 恢复 channel-watch（`by-dev-rootcoord-dml_N_<ID>v0`）与
  segment，看到僵尸 ID → 反复问 rootcoord → 刷 WARN。实测僵尸②被重试 **1768 次**。
- 若 rootcoord 启动时名字索引解析到已 drop 的条目 → `has_collection` 返回 false →
  后端再建一个同名集合 → **僵尸 +1，恶性循环**。

**首个僵尸的由来**：09-15 换 Embedding（768→1024 维），`milvus_store.py:88-101`
维度校验分支 `drop_collection` + 立即 `create_collection`。
**GC 被打断的原因**：compose 里 milvus 服务**没设 `stop_grace_period`**，Docker 默认只给
**10s** SIGTERM 就 SIGKILL，Milvus 优雅关闭 + GC 根本来不及。

**治本**（建议合并到一次维护窗口做，别在业务时段单独执行）：
1. `docker-compose down -v` 清空 etcd+minio volume → `up -d` → 重灌（约 6 分钟）。
2. 给 compose 的 milvus 服务补 `stop_grace_period: 60s`。
3. 停服顺序：先 backend 再 milvus，别直接 `docker restart gov-milvus`。
4. 少改 `VECTOR_DIM`（每改一次就多一个僵尸）。

**当前风险**：4 个同名僵尸仍在，名字→ID 解析依赖加载顺序，不保证下次重启还对。
复发就按上面 1~3 一次性处理。

**僵尸排查命令（下次直接用）**：
`docker exec gov-milvus-etcd etcdctl get --prefix --keys-only by-dev/meta/root-coord/database/collection-info/1/`
→ 若同一个集合名出现多个 ID，就是僵尸累积。再按
`by-dev/meta/datacoord-meta/s/<ID>` 分组统计 segment 数，最大的那个是当前有效的。
