## 问题：重启电脑后问什么都答「知识库暂无该业务政策」

用户反馈：重启电脑、按指南启动后，前端所有提问都返回兜底话术。

### 排查路径（每一步都有实证）

1. **先排除"库坏了"**：`docker-compose ps` 6 容器全 healthy；
   `/api/health` → `vector_store=milvus`、`doc_count=580`。库完好。
2. **看后端日志，抓到真凶**：
   ```
   [error] 检索失败：DashScope 向量化失败：HTTP 401: {"code":"InvalidApiKey",...}
   ```
   不是检索问题，是**向量化第一步就 401**，导致后续全链路无结果。
3. **比 key 长度/哈希**（沿用 09-14 的教训）：
   - 容器内：`len=117, sha8=944e1329, tail=u5tc46`
   - 两份 `.env`：`len=116, sha8=757cc6f7, tail=eZGuiQ`（且均为 LF，无 `\r`）
   → 容器拿到的**不是** `.env` 里的 key，而且长度差 1 位，像旧 key。
4. **判断哪个 key 有效**：拿 `.env` 的 key 直接打 DashScope compatible-mode
   embeddings → **HTTP 404 `model_not_supported`**（不是 401）→ **key 本身有效**。
5. **定位注入来源**：`docker-compose config` 在当前 shell 下解析出的是**正确的 116 位**，
   说明 `.env` 文件没问题、当前 shell 也没污染。
6. **查持久化环境变量**（关键一步）：`reg.exe` 被沙箱安全策略拦截，改用 python `winreg`：
   ```
   用户级(HKCU\Environment): 未设置
   系统级(HKLM\...\Session Manager\Environment): len=117 sha8=944e1329 tail=u5tc46  ← 命中！
   ```

### 根因

**docker-compose 的变量插值优先级是「shell / 持久环境变量 > `.env` 文件」。**

本机 Machine 级环境变量里残留了一个**失效的旧 `DASHSCOPE_API_KEY`**（117 位）。
`docker-compose.yml` 里写的是 `DASHSCOPE_API_KEY: ${DASHSCOPE_API_KEY:-}`，
于是每次 `up -d` 都取到旧 key，`.env` 被静默忽略 → 容器内 401 → 全部兜底话术。

**为什么重启后依然**：系统级环境变量持久化在注册表，重启不消失。
**为什么昨天测通了**：昨天 recreate 时的进程环境没继承到该变量（偶然）。

### 修复

**① 立即恢复**（当前干净环境 recreate）
```bash
docker-compose -f docker-compose.yml up -d --force-recreate backend
# 容器内 key 恢复为 116 位 / 757cc6f7
```

**② 代码层加固**（`docker-compose.yml`，backend 服务）
```yaml
  backend:
    container_name: gov-backend
    env_file:
      - .env          # 直接读文件注入，不经过 shell 插值
    environment:
      # DASHSCOPE_API_KEY / OPENAI_API_KEY 从这里移除，改由 env_file 提供
```
`env_file` 注入不经过变量替换，因此**无论环境里有什么同名变量，`.env` 始终说了算**。

**③ 加固验证（关键）**：故意在命令行前置一个假 key 再重建：
```bash
DASHSCOPE_API_KEY="sk-ws-FAKE_POLLUTED..." docker-compose -f docker-compose.yml up -d --force-recreate backend
# 容器内仍是 len=116 / 757cc6f7 → ✅ 挡住
```

**④ 彻底治本**（待用户执行，需管理员 PowerShell）：
```powershell
[Environment]::SetEnvironmentVariable('DASHSCOPE_API_KEY', $null, 'Machine')
```

### 复用要点

- **「改 `.env` 不生效」的排查顺序**：① 文件本身（长度/哈希/换行符）
  → ② `docker-compose config` 看插值结果 → ③ **持久化环境变量（HKCU + HKLM）**。
- **`${VAR}` 插值的优先级：shell / 持久环境变量 > `.env`**。密钥类变量一律走 `env_file` 最稳。
- 401 排查先比长度/哈希，别急着换 key；compatible-mode 打 embedding 返回 **404 说明 key 有效**。

## 口语化泛问改造：闸门改为「向量主导 + 泛问引导」

需求：群众用口语提问（"我想开个小店，要办啥"）时不再回"知识库暂无该业务政策"，改为按向量相似度匹配回答。

改动（backend，已实测生效）：
1. **自适应融合**（`milvus_store.search` / `vectorstore.search`）：
   关键词池最大值 < `KEYWORD_MIN_SCORE` 时判定"口语化、无术语重叠" → **只按向量分排序**；
   否则才做 0.45 向量 + 0.55 BM25 混合。
   原因：口语问法的 BM25 全是单二元组噪声（能给不相关文档打到 11 分），
   混合后噪声文档反而顶掉真正的语义命中（"开个小店"Top-1 从设立登记被挤成城乡居民养老）。
2. **候选补齐向量分**（milvus）：只靠 BM25 进池的候选原本 `vector_score=0`，
   现按 id 取回 embedding 本地算余弦 —— 否则"按向量判定"有洞（"北京有哪些景点"显示 0 分）。
3. **闸门 `_is_relevant`**：主判据改为 `vec >= VECTOR_MIN_SCORE`；
   兜底改为 `kw >= KEYWORD_MIN_SCORE 且 融合分 >= FUSED_MIN_SCORE`（两条件同时满足）。
4. **泛问引导**（新增 `_is_vague` / `_guide_answer`）：问题无业务实体词（`ENTITY_HINTS`）
   或 Top-1 向量分 < `VAGUE_VECTOR_MAX` → 列出最相近候选事项让用户确认，
   这是**引导不是拒答**，避免"怎么办证"硬答成居住证。
5. **Prompt 规则 7**：资料讲的是语义最相近事项时不得拒答，先写"您咨询的可能是《XX》"再作答。

阈值（768 维 vision-flash / 580 片段实测，写死在 compose 与两份 `.env`）：
`VECTOR_MIN_SCORE=0.73`（域外最高 0.716、口语化最低 0.737）、
`FUSED_MIN_SCORE=0.62`、`VAGUE_VECTOR_MAX=0.78`、`KEYWORD_MIN_SCORE=32.766` 不变。
标准问法 vec 0.83~0.93 / 口语化 0.71~0.91 / 纯域外 0.58~0.72。

新增脚本：`backend/scripts/probe_gate.py`（口语化/标准/域外分数探测，看 Top1-Top2 差）、
`scripts/qa_smoke.py`（宿主机端到端冒烟，打 8080）。换模型必须重新标定：
`calibrate_gate.py` 只覆盖标准问法，口语化样本必须靠 `probe_gate.py` 复核。

实测结果：开店→设立登记、店不开→注销、过户→转移登记、改名→变更、营业执照时限→设立登记
全部命中正解；"怎么办证/请问怎么办理"给候选引导；"今天天气/写诗"仍拒答。

## 17:20 修「当前大模型不可用，以下为知识库原文兜底回答」（qwen3.8-2.4t-a95b 强制思考链）

现象：容器起来后 `/api/health` 全绿，但每个问答都带"依据知识库原文生成的兜底回答"。
**注意：health 全绿 + 有答案 ≠ LLM 正常**——抽取式兜底也会拼出像样的答案，必须看日志。

根因（后端日志）：
```
[error] 大模型调用失败，使用抽取式兜底：Error code: 400 -
'<400> InternalError.Algo.InvalidParameter:
 The value of the enable_thinking parameter is restricted to True.'
```
`qwen3.8-2.4t-a95b` 把 `enable_thinking` **锁死为 True**，`llm.py` 传 False 直接 400。
（改模型时只验证了 health 与一条冒烟，而那条冒烟的答案其实是兜底拼的 → 误判上线。）

修复（`backend/app/services/llm.py`）：
1. `_is_thinking_param_error()`：异常文本含 `enable_thinking` 即判定为参数不兼容。
2. `OpenAICompatLLM.generate()` 加**翻转重试**：先按配置发 False，400 就翻成 True 重试；
   实例属性 `_thinking_forced` 记住结果，不会每个请求都白吃一次 400。
3. 重试时 `max_tokens` 抬到 `THINKING_MIN_TOKENS=8192`（思考 token 计入 max_tokens，
   沿用 4096 会把答案挤没）。
4. **关键加速**：思考模式默认单轮 141s（实测），加 `thinking_budget` 后降到 22~30s。
   新增配置 `LLM_THINKING_BUDGET`（config.py 默认 1024，0=不传）。实测裸问：
   budget=512 → 2.7s，budget=2048 → 3.3s；带 RAG context 的实际问答 22~30s。
   `_thinking_body()` 统一构造 `{"enable_thinking": True, "thinking_budget": N}`。

已同步 8 处：两份 `.env`、两个 `.env.example`、两份 compose、两份 README。
验证：124 passed；日志只剩 1 条预期 warn；`/api/chat` 出真实 LLM 答案（带 material_list）。

### 教训
- **换 LLM 后必须用"日志无 [error] 大模型调用失败"验收**，不能只看 health 和答案字面。
- 更快的判据：抽取式兜底的答案开头固定是「根据《XXX》，为您整理如下」，看到这句就是降级了。
