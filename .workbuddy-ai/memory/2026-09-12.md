1. **qwen3-vl-embedding 不支持 OpenAI 兼容模式**（404），必须走原生端点 `/api/v1/services/embeddings/multimodal-embedding/multimodal-embedding`，payload `{"input":{"contents":[{"text":...}]}}`，一次一条。
2. **该模型余弦基线很高**：领域内 0.78~0.89，领域外仍有 0.33~0.41 → 闸门阈值改为 `VECTOR_MIN_SCORE=0.55`、`KEYWORD_MIN_SCORE=25.0`（旧的 0.18/7.0 会放行"帮我写一首诗""北京景点"）。改后 5/5 域外全拦截。
3. **PDF 表格列名被误当成章节标题**：`材料名称/材料依据/材料形式/材料要求/材料下载/其他信息` 是列头不是章节，必须排除；政务 PDF 还有"导航块"（办理流程/网上办理流程/线下办理流程/材料清单 连续成行）导致标题错配，需再用正文特征词（法律法规名称/依据文号/原件/复印件…）做内容级纠正。
4. **材料抽取不能用"每行一条材料"**：PDF 会把单元格拆成多行。正确做法是「行号 → 名称行缓冲 → 遇 原件：/复印件：/纸质 等标记行收口」，并且**只在行号之后才收口**（`row_started`），否则会抽出"请表格文书""质/电子化"这类字段残片。
5. 判定顺序坑：`原件：1` 含冒号会被通用噪声规则先清掉缓冲 → 必须**先判列名噪声、再判收口标记、最后才判通用噪声**；且最小长度只在拼接完成后校验（"请书"只有 2 字）。
6. 流程/依据章节里也有"原件："字样，不能当材料表，否则抽出"审查标准"等噪声。
7. `GD00_广东省政务办事指南索引清单` 是管道生成的目录，会把各类问题都吸到它上面 → 导入时默认排除。

## 第 4 部分：调用模型切换为 qwen3.8-max

`DASHSCOPE_MODEL=qwen3.8-max`（`.env` 与 `.env.example` 均已改，API Key 一并写入 `.env`）。

### 关键结论：qwen3.8-max 是推理模型
- 响应里带 `reasoning_content`，说明默认开思考链；**单轮实测 185s**，直接撞破 60s 超时。
- 后果很隐蔽：检索其实成功了，但因为 LLM 超时走异常分支返回空串，前端显示成
  "知识库暂无该业务相关政策" —— **超时被误报成"无政策"**。
- 解决方案（全部已落地）：
  1. `LLM_TIMEOUT=300`（config.py 新增）
  2. `LLM_ENABLE_THINKING=false` → `extra_body={"enable_thinking": False}` 关闭思考链，
     实测延迟 **185s → 7~29s**
  3. `LLM_MAX_TOKENS=4096`，避免长答案被截断成半个 JSON
  4. 前端 `frontend/src/api/index.js` axios `timeout` 60s → **300000**
  5. `llm.py` 新增 `_rescue_answer()`：JSON 解析失败时用正则从截断文本里抢回 `answer` 字段
  6. `rag.py` 新增 `RAGService._fallback_answer()`：LLM 失败不再返回空答案，
     改为 `ExtractiveLLM` 依据已召回原文作答并追加"⚠️ 当前大模型不可用…"提示
  7. `OpenAICompatLLM` 接受 `name=`，health 现在正确显示 `dashscope:qwen3.8-max`

### 验证
- `/api/health` → `{"status":"ok","database":"PostgreSQL","vector_store":"milvus","doc_count":562,"llm_provider":"dashscope:qwen3.8-max","embedding_provider":"dashscope_native"}`
- 17/17 用例通过（12 域内 + 5 域外拒答），无 JSON 泄漏，延迟 7~29s
- 后续换模型只需改 `DASHSCOPE_MODEL`；推理模型务必同步检查上面 3 个超时/思考链参数。

### 修复的真 bug
1. **Nginx `proxy_read_timeout 120s`**：推理模型单轮可达 300s，Docker 部署时 Nginx 会先掐断 → 前端只见 504。改为 330s。
2. **compose 未下发关键配置**：`config.py` 默认值仍是 `qwen-plus` + 闸门 `0.18/7.0`（1024 维时代的），而 2560 维需要 `0.55/25.0`；compose 也没传 `DASHSCOPE_MODEL`、`LLM_TIMEOUT`、`LLM_ENABLE_THINKING`、`LLM_MAX_TOKENS`。已全部显式注入。**换 1024 维模型时必须同步改回 0.18/7.0。**
3. **`docker-compose.yml` 的 `depends_on` 让"只起后端前端"失效**：`up backend frontend` 会把 postgres/etcd/minio/milvus 一起拉起 → 改用 `docker-compose.host.yml`。
4. **溯源得分恒定**：`enrich_sections` 的召回查询是 `f"{doc_name}" + 章节名`，与用户问题无关，导致同一文档下补全出的章节得分恒定（表现为"问什么都是 0.8794/0.8614/0.8506"）。已把补全片段得分压到真实召回最高分之下。

### 补齐的缺失环节：意图感知重排（rerank）
前端执行链路里画了「重排」步骤，但代码里 `retrieve → 过滤 → 补全 → 生成` 根本没有重排。
**实测问题**：`实施依据/设定依据` 大段罗列法规名（…条例/…办法/…规定），是典型"关键词磁铁"——
不管问什么都排第一，把 `材料清单`/`办理流程` 挤到后面；"公积金""社保卡"这类库里没有的问题
也会因为命中某篇的"实施依据"（kw 37.17）而通过闸门。
**方案**（`rag.py::_rerank`）：按问题意图给章节加权 1.22~1.35，未问"依据"时对依据类章节 ×0.72；
只改 `h.score`（用于排序），**不动 `vector_score`/`keyword_score`**，因此 `_is_relevant` 的绝对分判定不受影响。
效果：材料类问题 Top1 从 `实施依据` 回到 `材料清单`（1.08，已夹到 0.9999 以内）。

### 踩坑
- **`ChatResponse` 没有 `hit` 字段**！写评测脚本时用 `r.get("hit")` 判断命中，结果 12 条域内全被误判"未命中"、
  5 条域外"假通过"（0.4s 就返回，说明压根没调 LLM）。只能用 `sources` 是否为空判断（未命中时后端直接返回空 sources）。
- **Docker 构建验证不了**：本机 Docker Hub 不可达（`dial tcp registry-1.docker.io:443` 超时），
  只有 `docker-compose` v1（无 `docker compose` v2）。已把配镜像加速器的方法写进 README。
- 提示词加了第 6 条：参考资料只是**顺带提及**某业务（如依据文件提到"推进异地就医备案"但没说要什么材料）
  也按"暂无该业务相关政策"处理，禁止用模型自身知识补全材料清单。

### 重排的两个坑（都是实测踩出来的）
1. **只按重排分全局排序会改变"命中哪篇文档"**：`enrich_sections` 用 `hits[0]` 当主文档，
   依据类降权后主文档被换成别的篇，"高校毕业生就业创业补贴"因此取到了"灵活就业社保补贴申领"的材料清单。
   → 改成**两级排序**：先按文档的**原始**最高分定文档顺序，再按重排分定文档内章节顺序
   （`h.meta["raw_score"]` 保存原始分，`hits.sort(key=lambda h: (-best_raw[h.doc_id], -h.score))`）。
2. **补全片段得分恒定**：见上，已压到真实召回最高分之下（`cap = best * 0.999`）。

### 容错补全
- `enrich_sections` 也会调 Embedding，但它在 `retrieve` 的 try 块**之外** → 故障时直接 500。已包 try，失败就用未补全结果继续。
- 新增 `RETRIEVAL_ERROR_ANSWER`（与 NO_HIT_ANSWER 区分）：检索侧故障要说"服务暂时不可用"，
  **不能**说"暂无该政策"，否则把服务故障误报成"库里没有"。
- `EMBED_TIMEOUT=30`：原来 Embedding 复用 `LLM_TIMEOUT=300`，一次挂起会阻塞 300s×重试次数。
  重试 3→4 次，退避改指数 `min(1.5*2**attempt, 8)`。
- 大模型偶尔漏输出 `required`（同一问题两次调用可能"必备 2 条"/"必备 0 条"）→ 为空时用
  `extract_material` 结果补齐。

### 环境坑（重要）
- **本环境有 `http_proxy=http://127.0.0.1:49416`**：后端进程一旦死了，
  对 127.0.0.1:8000 的请求会被代理转成 **502 Bad Gateway**（不是 connection refused），很容易误判。
- **后端必须用 `run_in_background` 启动**；用 `... &` 起的进程会随 Bash 工具调用结束被回收，
  现象是"启动后 health 200，随后所有请求 502"。

### 最终结果
`python scripts/eval_rag.py` → **17/17 通过**（12 域内命中正确文档 + 材料清单完整，5 域外全部拦截），

## 第 8 部分：Docker 部署从"不可达"误判 → 实测跑通

**此前结论错了**：之前 README 写"Docker Hub 不可达（`dial tcp registry-1.docker.io:443`）"，
实测是误判。排查链：

1. `curl https://registry-1.docker.io/v2/` → **401**。
   401 是 Registry v2 对未认证请求的正常应答，说明链路通（000 才是断）。
   加 `--noproxy '*'` 同样 401 → 宿主 shell 里的 `http_proxy` 不是障碍。
2. `docker pull hello-world` 成功 → 进一步证伪"不可达"。
3. **真正的两个原因**：
   - **命令用错**：本机只有独立版 `docker-compose` v5.5.1，**没有** `docker compose` v2 插件。
     写成 `docker compose -f ...` 会被 Docker 主 CLI 当全局 flag 解析 →
     `unknown shorthand flag: 'f' in -f`（退出码 125）。这是"看起来像网络问题"的假象源头之一。

### ⚠️ 核心 bug：clean_text 过激清洗

完整栈首次导入只出 382 片段，原管道同样语料 570，少 33%。分步量化定位：
- 原始 207,347 字符 → clean_text 后 147,744（**损失 59,603 = 28.7%**）
- chunk_text 后总和 184,654 ≈ 147,744 × 500/400 → **chunk_text 本身无损**（正好是重叠系数）
- 所以损失 100% 来自 clean_text

两个根因（都在 `app/utils/text.py`）：
1. 页眉正则 `r"^\s*第?\s*[0-9...]+\s*页?(...)?\s*$"` —— `第?`/`页?` 都可选，
   退化为"匹配任意纯数字行"，把**事项业务编码**（5442106041002）当页眉删掉
2. 去重判据是 `line in seen and len(line)<60`（全文任意重复短行），
   政务表单里合法重复的 `否`/`无` 被去重

修法：
- 页码正则拆成三条，都必须出现「页」或「N / 共 M」或「—— N ——」
- 去重改为只判**紧邻上一行**：`if lines and lines[-1] == line and len(line) < 60`
- 顺带删掉不再使用的 `seen` 集合

**效果**：清洗损失 28.7% → 0.7%（1,421 字符）；片段数 382 → **534**。
容器内实测 `--clear` 重导入 12 篇 → 534 片段，耗时 4m54s；
端到端问答 HTTP 200 / 18.8s，溯源最高 0.8899。

**新增回归测试** `tests/test_text_utils.py` 里 `TestCleanTextNoOverStrip` 5 项：
业务编码保留 / 纯短数字保留 / 非连续重复短值保留 / 真页码仍删除 / 连续重复仍去重。
→ `pytest` 从 58 passed 变 **63 passed**。

**两套分块口径差异（正常，不是 bug）**：本仓库原生导入 534，
原 rag_pipeline 的 RecursiveCharacterTextSplitter 得 570。
两者 chunk_size=500/overlap=100 相同，差异来自 NFKC 归一化 + 空行处理。
宿主 Milvus 现存 562 片段属后者，无内容损失，故未重建。

**收尾**：完整栈 `down -v` 清理，已恢复宿主模式栈 doc_count=562。
