# 2026-09-14 工作日志

## 排查「所有问题都答『知识库暂无该业务相关政策』」

### 现象
`docker-compose -f docker-compose.host.yml up -d` 启动后，网页问答对所有问题都返回
`知识库暂无该业务相关政策，请咨询线下政务窗口`。

### 三层根因（逐层实证）
1. **后端启动时 Milvus 未就绪 → 静默降级为空的内存向量库**
   - gov-backend 启动 05:20:32，milvus-standalone 启动 05:20:33，Milvus standalone 需数十秒才接受连接。
   - `get_vector_store()` 一次性初始化失败即降级 `MemoryVectorStore`（容器内无持久化文件 → 空）。
   - 日志证据：`[warn] Milvus 初始化失败，降级为内存向量库` + `[init] Vector store = memory (docs=0)`。
   - `RAGService.retrieve()` 首行 `if self.store.count() == 0: return []` → 检索恒空 → 全部走 NO_HIT 分支。
   - 关键误导点：降级后 `/api/health` 仍返回 200，故障被伪装成「知识库没有该政策」。
2. **宿主机 Milvus 的 `gov_docs` 集合本身已损坏**
   - `get_load_state` = Loading / progress 33，永久卡住；query/search 返回 503
     `channel not available`。
   - Milvus 日志：`failed load json key stats ... invalid local path:files/json_stats/3/.../meta.json`。
   - 数据卷 `D:\milnus\volumes\milvus\data` 布局与当前镜像 `milvusdb/milvus:v3.0.0` 期望不一致：
     段写在 `data/var/lib/milvus/data/insert_log/...`（多一层嵌套），json_stats 分散在
     `data/json_stats/` 与 `data/var/lib/milvus/data/json_stats/`，而服务端按 `<root>/files/json_stats/...` 查找。
   - 已验证 Milvus 实例本身正常：新建临时集合 → insert → load → search 全部 OK。
     （故故障是「这一个集合的数据」，不是实例。）
   - 副作用：`load_collection()` 无超时会**永久阻塞**，把后端卡死在 lifespan 启动阶段。
3. **DASHSCOPE_API_KEY 失效（HTTP 401 InvalidApiKey）**
   - `tongyi-embedding-vision-flash` 调用返回 `InvalidApiKey`，密钥在根 `.env` 与 `backend/.env` 中相同。
   - 意味着：即使修好前两项，重新入库与在线检索仍会失败（检索向量化必须走该接口）。

### 已做修复（backend 代码，3 处）

  `load_collection` 不再无限阻塞；失败记入 `self.load_error` 并打印排查指引。
- `app/services/vectorstore.py`：`BaseVectorStore.degraded` 标记；新增
  `_connect_with_retry()`（6 次 × 5s），解决 compose 同启时的竞态；降级时打印醒目告警。
- `app/services/rag.py`：`answer()` 在 NO_HIT 之前先判 `degraded` / `load_error`，
  返回 `RETRIEVAL_ERROR_ANSWER`（「检索服务暂时不可用」），不再把故障说成「库里没有」。

### 第 4 层根因（后续追加）：CRLF 把 `\r` 混进密钥 → 误判「密钥失效」
- 最初在容器内测 Embedding 得到 `HTTP 401 InvalidApiKey`，**但密钥本身是好的**。
- 决定性证据：宿主机直连 DashScope 四个端点（chat / text-embedding-v3 / v4 /
  tongyi-embedding-vision-flash 原生端点）**全部 200**。
- 真因：`.env` 与 `backend/.env` 都是 **CRLF**，密钥值实际是 117 位（尾部带 `\r`）。
  旧容器读到的就是 117 位版本 → DashScope 判 InvalidApiKey；重建后的容器读到的
  是 docker-compose 剥离 `\r` 后的 116 位版本 → 正常。
- 修复：两个 `.env` 全部转 LF（`.env` 37 处、`backend/.env` 87 处 CRLF → 0）。
- **教训**：报 401 不等于密钥过期，先 `len()` 一下密钥、再比对字节。

### 第 5 层根因（最终追加）：宿主 Milvus 重启即崩 + 无法从磁盘重载 → 换用项目自带 compose
- 实测 `docker restart milvus-standalone`：容器 **Exited (134)**，日志 `panic: etcdserver: leader changed`
  —— 内嵌 etcd 选主竞态，streamingnode 抢跑 `Session.checkIDExist` 的 Txn 直接 panic。需再 start 一次才起得来。
- 起来之后 `gov_docs` 依旧卡 `Loading/progress 33`：新写的集合也报
  `invalid local path:files/json_stats/3/<buildID>/.../107/meta.json`。
  实际文件在 `<localStorage.path>/json_stats/...`（`localStorage.path = /var/lib/milvus/data/`），
  服务端却按 `<root>/files/json_stats/...` 读 —— **写入路径与读取路径差一层 `files/`，是系统性不匹配，
  不是脏数据**。即：该 Milvus 每次重启后都必须重新 ingest 才能用。
- 结论：`D:\milnus` 那套（v3.0.0 + 内嵌 etcd + Windows 绑定挂载本地存储）不适合本项目。
- **已切换为项目自带的 `docker-compose.yml`**（milvusdb/milvus:v2.4.13 + 独立 etcd + MinIO +
  命名卷 + `depends_on: condition: service_healthy`）。镜像本地已有，零下载。
- 切换步骤与结果：
  1. `docker-compose -f docker-compose.host.yml down`
  2. `docker-compose -f docker-compose.yml up -d --build` → 6 容器全 healthy，后端启动零告警
  3. `docker exec gov-backend python scripts/ingest.py --dir /app/data/corpus --clear` → 580 片段
  4. **耐久性验证**：`down` 后 `up -d`（不带 --build，模拟开机）→ 知识库完好
     （`doc_count=580`，无 Milvus 告警），问答正常（居住证续期 sources=9；
     灵活就业补贴金额问题诚实答"语料未涉及具体金额"，未编造）

- 注意：切换后聊天历史落在新的 `gov-postgres`（命名卷 `postgres_data`），与之前 bigpg 里的记录不连续。

### 复用要点（下次遇到同类问题）
1. 先分清三种"答不出来"：库空(降级) / 库不可检索(段加载失败) / 上游 401。
   判据：`/api/health` 的 `vector_store` + `doc_count`，再看后端日志有无 `[warn]`。
2. Milvus 集合"卡 Loading"= `docker logs milvus-standalone | grep 'load segment failed'`；
   若报 `invalid local path`，说明存储布局与镜像不匹配，重灌数据也救不回来 → 换部署方案。
3. 401 先比 key 长度（`len()`），差 1 位基本是 CRLF 的 `\r`，不是 key 过期。
4. 改 `.env` 后必须 `--force-recreate`，`restart` 不重新读环境变量。
